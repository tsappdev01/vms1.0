Visitor Desk

A reception attendant puts an Emirates ID into a reader, the chip's own data appears on screen, they name the entity and the person being visited, and the entry is stamped. This is how that is built, and which of the constraints behind it were discovered rather than chosen.

Scope

Three modules were asked for. Two were specified and are built; the third has not been named yet, and nothing has been assumed in its place.

ModuleRouteWhat it doesState
Visitor Management / Insert card → read chip → show the visitor's data, photograph and signature → select entity → enter the person to visit → save with a date-time stamp. Built
Visitor Details by Entity /report Every stored field plus the stamp, grouped by entity, filtered by date range and entity, exportable and printable. Built
Third module — Not specified. Awaiting

Everything outside those two screens is deliberately absent — no visitor pre-registration, no badge printing, no host notification, no blacklist, no sign-out. This is a first increment against a real reader, not a reduced version of the full BRD.

Why it runs at the desk, not on a server

The Emirates ID is a contact smart card. Data comes off the chip over PC/SC through a locally attached reader — it is not photographed and it is not read by OCR. That single fact determines the shape of the whole application.

The toolkit's managed binding is a thin P/Invoke wrapper over a native EIDAToolkit.dll, and the process that loads it must be on the machine holding the reader. In Blazor Server, component code runs on the server side of the circuit — so if the server side is the reception PC, the component can call the toolkit directly.

Decision

One project, no API tier. A REST layer between the screen and the card would sit entirely inside one machine and buy nothing; if a second reception point is ever added, each gets its own instance pointed at the same database.

The capture path

A read is not one call. The toolkit returns both a set of field structures and a signed XML response, and both need work before they are fit to show or to trust.

Serialisation

The native toolkit context is single-threaded and expensive to create, so CardReaderService is a singleton holding one initialised context behind a SemaphoreSlim. Initialisation failure is remembered rather than retried, so a misconfigured desk reports the same clear reason every time instead of looping on a native init.

The two screens

New Visitor — four steps

The wizard mirrors what the attendant physically does, one step per action, with the reader's state shown before anything is asked of them.

  1. Insert card. Reader and card presence, toolkit version and licence expiry. "No card" and "no reader" are both normal idle states, not errors.
  2. Visitor information. An identity strip first — photograph, name in English and Arabic, ID number, nationality, card expiry, signature — answering who am I looking at before the field-by-field readout does. Then everything the chip returned, grouped exactly as the vendor's own tool groups it: Identity, Non-Modifiable Data, Home Address.
  3. Visit details. Entity from a dropdown read live from the database, person to visit as free text. Save stays disabled until both are set.
  4. Saved. Reference number, visitor, entity, person, and the stamp rendered in Gulf Standard Time.
Decision

Card fields are read-only on screen. The attendant cannot correct a name or a nationality, because the value's worth is that it came off the chip. Where a card is unreadable, the record carries CaptureMethod so a manual entry is never mistaken for a chip read.

Visitor Details by Entity

Grouped by entity, filtered by date range and entity, defaulting to the last thirty days. Fourteen columns do not fit a screen and the requirement is that the report carries every field, so each row is held to a single line at its natural column widths and the table scrolls inside its own container — with a shadow on whichever edge has more to see, so the overflow reads as scrollable rather than clipped. The date range is inclusive of the whole closing day in GST, because that is what someone means by a date on a report. Export is CSV with a UTF-8 byte-order mark, so Excel renders the Arabic name rather than mangling it a second time, and every value is checked for a leading =, +, - or @ so a name cannot execute as a formula when the file is opened.

The entity filter keeps a deactivated entity for as long as it still has visits behind it, so a report over an earlier period can still be narrowed to one.

The shell and the brand

Both screens sit in one shell: a sidebar carrying the Dubai Investments lockup and the two routes, and a header naming the office and holding a Gulf Standard Time clock. The clock ticks in the browser — a per-second server render for a wall clock would be circuit traffic for nothing.

The palette is the corporate mark's two colours. Navy #0e3453 carries action — the primary button, the active route, the current step. Gold #b8912e carries emphasis — the wordmark's second line, and a field that held data where its neighbours did not. Neither is spent on anything else, which is what keeps them meaning something. In dark mode navy becomes the ground, so it cannot also be the action colour; the accent lifts to a legible blue and every token is declared before either the media query or the data-theme block redefines it.

Decision

The artwork lives in exactly one file, wwwroot/brand/di-mark.svg, currently a placeholder rendition drawn to the brand colours. The sidebar and the favicon both point at it and nothing else references it, so dropping the official asset over that one file updates the whole application.

Deliberately absent

The reference layout carried a panel reading "all visitor data is secure and encrypted." It is not — see section 9 — so the three panels below the reader state say what the system actually does instead: identity comes off the chip, two fields are typed, each entry is stamped. An interface should not assert a control that does not exist.

What the chip actually gives

Read from the card: non-modifiable data, the photograph, the holder's signature image and the home address. Modifiable data — occupation, sponsor, passport details — is deliberately not requested. It is on the chip, and it is none of a visitor log's business.

Unresolved

"Fetch home address" was an explicit requirement, and on the card tested every postal field came back blank — only mobile and email carried anything. It is not yet known whether that is this card or every card. Until a second card says otherwise, the screen states "No postal address held on this card" rather than rendering nine empty boxes that look like a failed read, and highlights the two fields that did carry data.

Data model

Two tables in schema vms. Card values are stored exactly as the chip presented them, including the dates, which arrive as strings — so the record reflects what was read rather than an interpretation of it.

The remaining twenty-odd columns are the card fields listed in section 5, all nullable, all capped at their observed lengths. Nullable is not laziness: the card in section 5 proves most of them can be absent.

Schema, reference data and configuration

Three kinds of state, three owners. Conflating them is what made the first attempt fail on a database that already existed.

KindOwnerChanged by
Table schema Data/DbBootstrapper.cs Editing the EF model. DDL is generated from it at startup, so there is no second copy of the schema to drift.
Entity list db/seed_entities.sql A SQL insert and a page refresh. Never a rebuild — the list of group companies must not need a deployment.
Toolkit config appsettings.Development.json Per machine. Left blank, the app searches for a folder holding config_li, preferring one that also has config_ag.
Discovered the hard way

EnsureCreated does not do what its name suggests. It creates the schema only when it creates the database, and does nothing at all against a database that already exists — missing tables included. VMS existed, so it returned false silently and the first query failed with Invalid object name 'vms.Entity'. Likewise HasData runs only when a table is created, so it can never deliver a changed reference list.

The bootstrapper is honest about its limits: it creates tables that are absent and never alters ones that are present. If it finds the model half-applied it throws with the list of missing tables rather than starting an application whose reports would be incomplete. Once the database holds anything that cannot be dropped, this gives way to EF migrations.

Constraints discovered, not chosen

Each of these cost a debugging cycle and each now shapes code. They are recorded because the next person will otherwise pay for them again.

SymptomCauseConsequence in the design
Invalid or incomplete configuration data The toolkit config is newline-separated key = value. The SDK's own quickstart README documents a JSON example, which the toolkit rejects. Config is built as key = value, with config_directory pointing at quickstart\64 rather than the bundle folder.
Failed to get response from server Licence type PRE-PRODUCTION, HTTP 401 licence not found or not active. The telemetry POST is enforced, so read_publicdata_offline does not avoid the Validation Gateway. No degraded offline mode is offered, because there isn't one. Network reachability to ICP is a hard prerequisite. Resolved by ICP's IDCARDOFFLINE_config_2026-04-14 bundle.
Unable to load DLL 'EIDAToolkit.dll' (0x8007007E) The managed binding loaded; the native library and its thirteen companions were not beside the executable. The build copies them from the SDK, warns if they are missing, and the runtime error names the missing native files rather than the assembly.

On Windows any PC/SC-compliant reader works through the generic plugin — the confirmed unit is an ACS ACR39U ICC Reader 0. Mobile is different: there the reader must match a shipped plugin. Toolkits exist for Android and iOS as well as Windows, so a mobile client stays possible; the Windows binding is the only one needing no binding layer.

Security posture, stated plainly

This increment was built to prove a card read end to end, and its protections are the ones that fell out of that. The gaps below are real and are listed so they are decided rather than discovered.

What is in place

  • Request identifiers are 40 cryptographically random bytes, and a response that does not echo one is rejected.
  • Response XML is parsed with DTD processing prohibited and no resolver, so a card response cannot pull an external entity.
  • Modifiable card data — passport, sponsor, occupation — is never requested, so it is never stored.
  • CSV export neutralises formula injection.
  • Card values are read-only on screen; nothing that came off the chip can be edited.

What is not

Gap · no authentication

There is no sign-in and no roles. Anyone who can reach the application can read every visitor record. This is defensible only while it runs on one attended desk, and it is the first thing to fix before a second machine or any wider network exposure.

Gap · plaintext personal data

Emirates ID numbers, dates of birth, photographs and signatures are stored unencrypted and unmasked, with no retention limit. Transparent database encryption, column encryption for the ID number, and a retention job are all outstanding. The connection string uses Windows authentication and TrustServerCertificate=True — acceptable inside UAT, not for production.

Gap · no audit trail

Reads and exports are not logged, so there is no record of who looked at a visitor's data.

One capability worth adopting deliberately: the toolkit can assert that a card is genuine and not reported lost or stolen. Neither check is called today. Both are cheap and both are the difference between recording an identity and verifying one.

Prerequisites

Everything below is per reception machine.

  1. x64 Windows, with the Smart Card service running. The host process must be x64 — the binding P/Invokes an x64 native library.
  2. A PC/SC reader, visible to SCardListReaders. Any compliant unit; the generic plugin covers it.
  3. The ICP config bundle, in a folder holding config_li and config_ag. Licence expiry is monitored on screen — the current one runs to 29 July 2027.
  4. Network reach to the ICP Validation Gateway. Not optional, offline mode notwithstanding.
  5. The native toolkit DLLs beside the executable. The build copies them and warns if the SDK folder is absent.
  6. A connection to UATWEB01 · VMS under an account that may create tables on first run.

Then db/seed_entities.sql for the entity list, and the application on https://localhost:7100.
